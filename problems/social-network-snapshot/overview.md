# 整体思路

**一句话。** 主表是"用户 → 关注集合"的邻接表，快照是它逐个集合复制出来的不可改副本，外加一张反向表；所有查询只看快照自己那两张表。

**各问是叠加关系。** 第一问定下主表和快照复制。第二问只在 Snapshot 构造函数里多建一张反向表，加两个取行的方法。第三问只在 Snapshot 上多一个 recommend，用第一问的正向表。主表三问不改。

## 全部状态转移

| 当前状态 | 触发 | 条件 | 下一状态 |
|---|---|---|---|
| 用户不存在 | add_user | | 存在，关注集合为空 |
| 用户存在 | add_user | | ValueError，不变 |
| A 未关注 B | follow(A, B) | 两者存在，A ≠ B | A 关注 B |
| A 关注 B | follow(A, B) | | 不变 |
| 任意 | follow(A, A) | | 不变 |
| 任意 | follow，任一方不存在 | | ValueError，不变 |
| 任意 | create_snapshot | | 主表不变，新快照固定为此刻状态 |
| 快照 | 任何操作 | | 永不变 |

## 数据结构

| 结构 | 存什么 | 回答什么问题 | 第几问出现 |
|---|---|---|---|
| SocialNetwork._following | 用户 → set(关注的人) | 现在谁关注谁 | 1 |
| Snapshot._following | 用户 → frozenset(关注的人) | 快照时刻 A 是否关注 B；A 关注谁 | 1 |
| Snapshot._followers | 用户 → frozenset(关注他的人) | 快照时刻谁关注 A | 2 |
| recommend 里的 count | 候选 → 中间人数 | 排序 | 3 |

## 面试节奏

- 前 2 分钟：说"有向图，邻接表存，快照是逐集合复制的副本"。确认不存在用户的查询口径和名单顺序。
- 8 分钟：写主表和 Snapshot 构造加 is_following。写完先跑"快照后 follow 看不到"那条测试。
- 8 分钟：反向表和两个取行方法。跑正反表一致性测试。
- 8 分钟：recommend。跑题面例子。
- 留 5 分钟：讲状态表，说"建快照抄全表，大了要优化"。
- 剩余：追问。

## 常见追问

| 追问 | 答法 |
|---|---|
| 建快照抄全表太贵 | 写时复制：主表集合用 frozenset，follow 换新集合，快照只抄外层 |
| 还是贵 | 边记起止时间，快照只是版本号，查询二分；就是时间戳版 |
| 快照很多、只想存变化 | 快照存相对上一个的差量，定期合成一张全表 |
| 并发 | 读写锁：follow 独占，建快照和查询共享；快照本身不可改，查快照不用锁 |
| unfollow | 主表集合里删掉；快照不受影响 |
| 推荐更聪明 | 按边的时间加权（要时间戳）；扩 3-hop；离线算好存 top-N |
| 大 V | 每个中间人只取前 N 个 |
| 延迟建反向表 | 第一次 get_followers 时建，省没人查时的开销，多一个状态要管 |
