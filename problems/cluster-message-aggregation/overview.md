# 整体思路

**一句话。** 每个节点只做一件事：收到请求就转发给孩子并记下"我在等谁"，收到回复就按孩子 id 存进字典，字典条目数等于孩子数时按 children 顺序合并、往上发或者打印。之后每一问都是给这条流程加一个键（操作名、请求编号）或者加一条分支（重复、超时、失败），流程本身不变。

**六问是叠加关系。** 第一问搭出"往下广播、往上汇总"的流程；第二问把汇总值从数字换成字符串并要求顺序；第三问把两种操作合并成一个合并函数加一套流程；第四问给每个请求一个编号让多个请求能同时跑；第五问加超时重发、去重、失败上报；第六问加锁并验证深树不递归。

## 核心不变量

每个节点、每个请求上只有一条进度记录，下面四条在每一问都成立。

| 不变量 | 含义 | 从第几问起 |
|---|---|---|
| 先准备状态，再发消息 | 回复不可能先于状态初始化到达 | 一 |
| 收到请求后立刻检查一次完成 | 没有孩子的节点也能完成，n=1 的根也能打印 | 一 |
| 回复按孩子 id 存，按 children 顺序取 | 到达顺序不影响输出，重复回复不重复计数 | 二、三 |
| 完成就删进度，最终消息另存一份 | 内存不随请求数增长，父亲重问能原样重发 | 四、五 |

## 数据结构

| 结构 | 存什么 | 回答什么问题 | 第几问出现 |
|---|---|---|---|
| count_replies、count_sum | 收到几个回复、加起来多少 | count 收齐了没、总数多少 | 一 |
| topo_replies（字典） | 孩子 id 到子树字符串 | topology 收齐了没、按什么顺序拼 | 二 |
| OPS（字典） | 操作名到合并函数 | 这种操作怎么算自己的结果 | 三 |
| pending（字典） | 请求编号到 Pending（操作名、replies、attempts） | 这个请求在本节点进行到哪 | 三、四 |
| next_seq | 根发过几个请求 | 下一个请求编号是什么 | 四 |
| done（有上限的有序字典） | 请求编号到最终发给父亲的消息 | 父亲重问时回什么 | 五 |
| 定时器 | (到期时刻, 节点, 请求编号) | 哪个请求该重发了 | 五 |
| lock | 每节点一把 | 两条消息同时到怎么排队 | 六 |

## 面试节奏

- 前 3 分钟，口头定口径：消息格式自己定，请求和回复用前缀区分；到达顺序不保证；先按一次一个请求、消息不丢、单线程做，后面逐个放开。问面试官 from_id 到底是字符串还是整数。
- 接着 15 分钟写第一问：先写状态字段，再写 receive_message 的两个分支，再写完成检查。写完立刻说两个边界：没有孩子的节点、根自己是叶子。
- 再 10 分钟写第二问：加字典、加两个分支、按 children 顺序拼。写完主动说"两种操作流程一样，可以合并"，时间够就做第三问的重构，不够就口头说。
- 留 5 分钟写测试：题面的例子、单节点、lifo 投递顺序验证 children 顺序。
- 剩下时间按追问走：第四问改 pending 的键并加编号，第五问讲超时重发和 done 缓存，第六问讲锁和不递归。

## 常见追问

| 追问 | 答法 |
|---|---|
| 两次 count 同时来 | 请求编号，状态按编号分开存，做完就删 |
| 消息丢了 | 定时器超时后只给没回的孩子重发；孩子收到重复请求回存好的结果；父亲收到重复回复字典覆盖 |
| 节点挂了 | 重发到上限后报 ERR 往上传，根打印失败和哪个节点联系不上 |
| 超时值怎么定 | 大于子树最深路径一次往返；太短会误判并消耗重试次数；改进是孩子回"还在算" |
| 多线程 | 每节点一把锁，receive_message 和 on_timer 整个包住；发消息不等对方，不会死锁 |
| 一万节点的链 | 消息驱动不递归，每跳一次方法调用；同步等待的写法会卡死且爆栈 |
| 消息数、延迟 | 每请求 2(n-1) 条；延迟是树深那么多轮往返 |
| 再加一种操作 | 往 OPS 加一个合并函数，流程不动 |
| id 含特殊字符 | 冒号分隔会拆错，换 JSON 或长度前缀编码 |
| 客户端分不清哪个结果对应哪个请求 | 题面只要求打印结果；要分清就打印里带请求编号 |
| 操作进行中树在变 | 现在得到的是各节点被问到那一刻的快照拼起来的，不是同一时刻；要一致快照得先冻结再问 |
