# 第三问：两种操作合并成一套流程

## 面试官给的骨架

接口不变。这一问通常不是面试官出的新要求，而是你做完第二问主动提的："两种操作的消息流程一模一样，我把它抽成一套，操作只提供合并函数。"也可能面试官问"再加一种操作要改哪里"。

## 思路

**开口先定的口径。**

1. 一种操作等于一个合并函数：输入是自己这个节点和"孩子们按 children 顺序排好的结果列表"，输出是自己的结果字符串。叶子传进来的是空列表，所以叶子的值也从这个函数出，不用单独写。
2. 消息格式统一：请求就是操作名，回复是 "RES:操作名:结果"。外部客户端发的也是操作名，所以根收到的和内部节点收到的请求长一样，一个分支处理。
3. 进行中的状态按操作名分开存：pending 是一个字典，操作名到 {孩子 id: 结果}。count 和 topology 可以同时在跑，互不干扰。

**合并函数两个。** combine_count：1 加上所有孩子结果转成整数的和。combine_topology：没孩子返回自己 id，有孩子返回 id(用逗号连接孩子结果)。注册在字典 OPS 里，操作名到函数。

**receive_message 只剩两个分支。** 以 "RES:" 开头的是回复：拆出操作名和结果，存进 pending[操作名][from_id]，调完成检查。其他的是请求：操作名不在 OPS 里就报错；在的话 pending[操作名] 置为空字典，给每个孩子转发同一条请求，调完成检查。

**完成检查 _finish_if_ready(操作名)。** 字典条目数小于孩子数就返回。否则按 self.children 顺序取出结果列表，调 OPS[操作名] 算出自己的结果，删掉 pending[操作名]，根打印，不是根就发 "RES:操作名:结果" 给父亲。

**count 为什么也改成字典。** 第一问的两个数字在这里换成字典，是为了两种操作走同一段代码。附带的好处：第五问里同一个孩子的回复可能到两次，字典按孩子 id 存，第二次覆盖第一次，不会加两遍；数字计数器做不到。

**收到不在等的回复怎么办。** pending 里没有这个操作名时直接丢弃。这一问里不会发生，第五问重发之后会出现迟到的回复，提前把这条写上。

**加一种新操作走一遍。** 比如"最大深度"：叶子 1，非叶子 1 加孩子里最大的。只需要往 OPS 里加一行，消息流程一行不改。测试里加了这个操作，题面的树算出 4，路径是 1 到 3 到 6 到 7。

**复杂度。** 和前两问一样。

## 常见疑问

### 合并函数为什么接收"按顺序排好的列表"而不是字典

**两种接口的区别。** 一种是把 {孩子 id: 结果} 字典直接给合并函数，让它自己排序；另一种是流程先按 children 排好，给它一个列表。我选第二种，理由是"按 children 顺序"是题面对所有操作的统一要求，放在流程里只写一次；每个合并函数就不用各自记得排序，少一处出错的地方。

**用 topology 看。** 流程收到 {"6": "6(7)", "5": "5"}，按 children [5, 6] 排成 ["5", "6(7)"] 再交给 combine_topology，它只管拼 3(5,6(7))。换成 count，列表是 ["1", "2"]，combine_count 只管加。

| 操作 | 流程给的列表，已按 children 排 | 合并函数算出 |
|---|---|---|
| count，节点 3 | ["1", "2"] | "4" |
| topology，节点 3 | ["5", "6(7)"] | "3(5,6(7))" |
| count，叶子 7 | [] | "1" |
| topology，叶子 7 | [] | "7" |

### 两种操作同时跑为什么这一问就可以

pending 的键是操作名，count 和 topology 各占一个键，回复消息里带操作名，归到各自的字典里。所以 count 和 topology 同时发到根，两个都能算对，测试 test_count_and_topology_at_the_same_time 验证了这点。两个 count 同时发就不行，它们共用 pending["count"]，第四问解决。
