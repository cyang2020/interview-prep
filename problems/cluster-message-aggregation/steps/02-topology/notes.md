# 第二问：topology，按 children 顺序拼字符串

## 面试官给的骨架

接口不变，多支持一种消息 "topology"。根最后打印的格式：叶子是自己的 id；非叶子是 id(孩子1的结果,孩子2的结果,...)，孩子顺序按 children 列表。

## 思路

**开口先定的口径。**

1. 输出顺序按 children 列表，不按回复到达顺序。这决定了不能收到一个拼一个，要先存起来。
2. 回复消息要带一个字符串，格式 "topology_result:字符串"。字符串里有括号和逗号，没有冒号，所以切掉固定前缀就是结果。如果面试官说 id 可以是任意字符串，就换成长度前缀或者 JSON。

**和 count 的区别只有两处。** 叶子的值：count 是 1，topology 是自己的 id。合并方式：count 是加起来加 1，topology 是 id + "(" + 用逗号连接 + ")"。消息流程、完成条件、根打印的判断全部一样。

**状态换一种存法。** count 用两个数字就够，因为加法不分先后。topology 要按顺序拼，所以用一个字典 topo_replies：孩子 id 到它回来的字符串。收齐的判断变成"字典里的条目数等于孩子数"。拼的时候按 self.children 的顺序逐个从字典取，不按到达顺序。

**为什么不能收到一个拼一个。** 根给 2、3 发请求，3 的子树回复可能先到。收到一个拼一个会得到 1(3(5,6(7)),2(4))，和题面要求的 1(2(4),3(5,6(7))) 不一样。测试里用 lifo 投递顺序，也就是后发的先到，专门造这个情况。

**用节点 3 走一遍，6 的回复先到。**

| 步骤 | 3 收到什么 | topo_replies | 动作 |
|---|---|---|---|
| 1 | "topology" | {} | 给 5、6 发 "topology" |
| 2 | 6 回的 "topology_result:6(7)" | {"6": "6(7)"} | 1 个，还差 1 个 |
| 3 | 5 回的 "topology_result:5" | {"6": "6(7)", "5": "5"} | 收齐，按 children 顺序 [5, 6] 取，拼成 3(5,6(7)) |

**count 为什么这一问不改成字典。** 两个数字够用，不动它。第三问把两种操作合并时会统一改成字典，因为字典同时解决顺序和去重，第五问要靠它去重。

**复杂度。** 消息数还是 2(n-1)。每个节点拼字符串的代价是它子树的字符串长度，根上是整棵树的字符串长度，大约 n 乘 id 的平均长度。n 一万，几万个字符，没问题。

## 常见疑问

### 回复里的字符串会不会和分隔符冲突

**消息是怎么拆的。** 收到 "topology_result:3(5,6(7))"，代码按前缀长度切掉 "topology_result:"，剩下的整段就是结果，不再按冒号拆。所以结果里有多少括号逗号都没关系，只要 id 里没有冒号。

**如果 id 可以含任意字符。** 比如 id 是 "a:b"，前缀切法还能用，因为只切固定前缀。但第四问要在消息里加请求编号，就要按冒号拆多段，这时 id 里的冒号会拆错。面试里说一句：id 不可控就用 JSON 编码整条消息，或者"长度:内容"的方式。题面保证 id 是 0 到 n-1 的数字字符串，所以这里不做。

| 消息 | 怎么拆 | 拆出来 |
|---|---|---|
| "topology_result:3(5,6(7))" | 切掉固定前缀 | "3(5,6(7))" |
| "topology_result:5" | 切掉固定前缀 | "5" |
| "count_result:4" | 切掉固定前缀，转整数 | 4 |
